# BACKEND_SPEC.md — FastAPI Backend Implementation Guide
**Owner:** P1 + P5 (you). **Scope:** L2 (API/Application) and L3 (Domain/Intelligence) layers only.
**Contracts you must honor, not redefine:** `API_SPEC.md`, `DATA_SCHEMA.md`, `ML_GIS_CONTRACTS.md`.
**Do not touch:** React code (`FRONTEND_SPEC.md`), model internals (`ML_SPEC.md`), spatial algorithm internals (`GIS_SPEC.md`). You call into P2's and P3's modules through the interfaces defined in `ML_GIS_CONTRACTS.md` — you do not reimplement their logic here.

---

## Tech
FastAPI, Python, PostgreSQL (SQLAlchemy or similar ORM), pytest, Postman for manual contract testing.

## Directory structure (suggested)
```
backend/
  app/
    api/            # routers only — thin, no business logic (L2)
      auth.py
      crimes.py
      atms.py
      transactions.py
      predictions.py
      alerts.py
      dashboard.py
      intelligence.py
    domain/         # business/domain logic (L3), framework-agnostic — orchestration ONLY, no scoring/spatial math
      complaint_processing.py
      prediction_orchestration.py   # fetches data, calls ModelInterface + SpatialInterface, persists, returns
      alert_generation.py           # applies the ADR-006 threshold to already-scored results — does not compute risk_score itself
      intelligence_generation.py    # assembles the /api/intelligence/{crime_id} payload from already-persisted data
    interfaces/
      model_interface.py     # ABC the ML module implements — see ML_GIS_CONTRACTS.md
      spatial_interface.py   # ABC the GIS module implements
    models/         # SQLAlchemy models mirroring DATA_SCHEMA.md exactly
    schemas/        # Pydantic request/response models mirroring API_SPEC.md exactly
    core/           # config, security/auth, db session
  tests/
```

## Layer discipline
- **Routers (`api/`)**: parse request → call one domain function → return response shaped exactly per `API_SPEC.md`. No feature engineering, no scoring math, no spatial math here.
- **Domain (`domain/`)**: orchestrates — e.g., `prediction_orchestration.py` implements the synchronous flow in `ARCHITECTURE.md` §6 (retrieve complaint → retrieve ATMs → retrieve transactions → call ML interface → call spatial interface → persist → return).
- **Interfaces**: `ModelInterface` and `SpatialInterface` are the only things domain code calls to reach P2/P3's work. This is what makes the model/spatial logic swappable per `ARCHITECTURE.md` §3.
- **No `risk_scoring.py` or `hotspot_analysis.py` in this module.** An earlier draft of this directory listed both — they duplicated P2's scoring logic and P3's hotspot detection, which meant two people could end up implementing the same thing differently. Scoring lives only behind `ModelInterface`; hotspot/density logic lives only behind `SpatialInterface`. If a dashboard aggregate needs hotspot-style output, call `SpatialInterface`, don't reimplement it here.
- **Fetching data for the interfaces is the domain layer's job**, per the fix in `GIS_SPEC.md`/`ML_GIS_CONTRACTS.md`: `prediction_orchestration.py` fetches `atms`, recent `crimes`, and `transactions` rows itself and passes them as plain arguments into `SpatialInterface` and `ModelInterface` calls. Neither of those modules queries the database directly.

## Endpoint implementation checklist (per `API_SPEC.md` group)
- [ ] `/api/auth/*` — JWT issue/verify, role embedded in token
- [ ] `/api/crimes/*` — CRUD/list per schema
- [ ] `/api/atms/*` — list/detail, optional bbox filter
- [ ] `/api/transactions/*` — filterable list (synthetic data for MVP)
- [ ] `/api/predictions/{crime_id}` (POST/GET) — implements the 8-step flow in `ARCHITECTURE.md` §6
- [ ] `/api/alerts/*` — list + acknowledge, generated by `alert_generation.py` per the threshold and severity mapping in `ADRS.md` ADR-006 (`risk_score >= 0.4 AND confidence >= 0.5`) — do not invent a different threshold at implementation time
- [ ] `/api/dashboard/summary` — aggregate queries only, no new business logic
- [ ] `/api/intelligence/{crime_id}` — joins prediction + evidence + explanation into one payload

## Auth & RBAC `[MVP TARGET]`
Roles: `investigator`, `bank_analyst`, `administrator` (see `DATA_SCHEMA.md#users`). Enforce role checks in routers via a dependency, not scattered `if` checks. Principle: users only see information appropriate to their role. This is planned, not yet built — do not describe JWT/RBAC as `[IMPLEMENTED]` in any doc, comment, or demo script until it's actually wired end-to-end.

## Failure handling (must implement, not skip)
Per `ARCHITECTURE.md` §10 — handle explicitly: missing coordinates, no nearby ATM, insufficient historical data, no transaction activity, duplicate complaint, invalid transaction data, ML/spatial module unavailable, low-confidence result (return `insufficient_confidence`, don't fabricate), malformed input (422 with clear error body per `API_SPEC.md` error shape).

## Audit logging
Every state-changing or sensitive-read action writes an `audit_logs` row (login, prediction generation, prediction viewed, alert generated/acknowledged, intelligence report created, admin action, data modification). Implement as a lightweight decorator/dependency, not copy-pasted per endpoint.

## Testing
pytest for domain logic (pure functions, no HTTP), Postman collection mirroring `API_SPEC.md` for contract-level testing so P4/P2/P3 can validate against a running backend.

## What NOT to build here
No message brokers, no async task workers, no Kubernetes/Docker Swarm orchestration, no GraphQL layer, no PostGIS — unless `ADRS.md` has an entry justifying it. This is a modular monolith (see `ARCHITECTURE.md` §7).
